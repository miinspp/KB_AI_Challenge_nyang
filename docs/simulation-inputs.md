# 금융 시뮬레이션 입력 명세

## 현재 화면에서 계산 엔진으로 전달되는 값

| 구분 | 필드 | 현재 출처 | 시뮬레이션 반영 |
| --- | --- | --- | --- |
| 매출 | `monthlySales`, `monthlySalesMonths` | 홈택스 연동 목업의 최근 12개월 월별 매출 | 매출 추세, 월별 계절성, 변동성, 12개월 매출 전망 |
| 비용 | `monthlyExpenseHistory` | 홈택스 월별 임대료·인건비·매입비·카드수수료·기타비용 | 실제 월평균 고정비·변동비와 비용 변동성 |
| 보유 현금 | `currentCash` | KB 연동 계좌별 잔액 합계, 미연동 시 직접 입력 | 시작 현금과 안전자금 위험 |
| 계좌 현금 흐름 | `monthlyAccountCashFlows` | KB 연동 월별 입금·출금 합계 | 장부상 현금 흐름과의 차이를 위험 계산의 추가 변동성으로 반영 |
| 기존 대출 잔액 | `existingDebtBalance` | KB 연동 대출별 잔액 합계, 미연동 시 직접 입력 | 대환 가능 여부, 기존 상환 스케줄 |
| 기존 대출 유무 | `hasExistingDebt` | 직접 선택 | `YES`면 대출 4개 필드 필수, `NONE`이면 사용자 확인 후 명시적 0 전달 |
| 기존 월 상환액 | `existingMonthlyPayment` | KB 계좌 연동 목업 또는 직접 입력 | 기존 월 현금 유출과 상환부담 계산 |
| 기존 대출 목록 | `existingLoans[]` | KB 연동의 대출별 잔액·금리·상환방식·상환액·만기 | 대출별 월 상환 일정 합산 |
| 기존 대출 금리 | `existingLoanInterestRate` | KB 연동 대출별 금리, 미연동 시 직접 입력 | 기존 원리금 스케줄 및 대환 비교 |
| 기존 대출 잔여 기간 | `existingLoanRemainingMonths` | KB 연동 대출별 만기, 미연동 시 직접 입력 | 상환 종료 시점과 만기 잔액 반영 |
| 사업장 정보 | `industryCode`, `areaText`, `areaType`, `bizAgeYears` | 직접 입력/홈택스 목업 | 진단 비교군, 지역·업력 추천 조건 |
| 세금 대비 적립 | `taxReserveRatio` | 최근 1년 실제 세금 납부액 ÷ 최근 연환산 매출 | 납부 이력이 없으면 0%로 가정하지 않고 계산에서 제외 |
| 세금 납부 일정 | `scheduledTaxPayments[]` | 홈택스 납부 예정 세목·납부월·금액 | 예정된 달의 실제 현금 유출로 우선 반영 |
| 사용자 선택 금액 | `desiredFundingMan`, `desiredGrantUseMan`, `desiredSavingsMan` | 직접 입력 | 희망 대출액, 지원금 활용액, 월 적금액 |
| 추천 선택 | `sourceType`, `id`, `eligibilityStatus`, `duplicateGroup` | 추천 API 결과 | 카탈로그 조건, 자격상태, 중복가입 검증 |

현재 KB/홈택스 버튼은 외부 API를 실제 호출하지 않는 데모 목업이다. 홈택스는 최근 12개월의 월별 매출과 비용 항목, 최근 세금 납부액, 예정 세금 납부일을 제공한다. KB는 계좌별 잔액과 월별 입출금 합계, 대출별 잔액·금리·상환방식·월 상환액·만기일을 제공한다. 시뮬레이션은 연결된 계좌 잔액 합계를 현재 현금으로 사용한다. 월별 입출금은 매출·비용에 다시 더하지 않고 장부상 현금 흐름과의 잔차 변동성을 위험 분석에만 반영해 이중 계산을 막는다.

## Python 추천 모델과 시뮬레이터 연결 규칙

- 추천 API의 단일 `products[]` 목록만 시뮬레이터 장착 후보로 사용한다. 이전 Java 추천 응답의 `policies[]`/`products[]` 분리 구조와 정적 상품 폴백은 사용하지 않는다.
- 추천 결과의 `source: "KB"`는 `sourceType: "KB_PRODUCT"`로, `source: "GOV"`는 `sourceType: "SEOUL_POLICY"`로 변환한다.
- `id`는 변경하지 않는다. 백엔드는 이 식별자로 KB 상품 및 정책 카탈로그에서 금액, 금리, 기간, 지원 효과의 기본값을 찾는다.
- 추천 응답은 자격을 확정할 근거가 부족하면 `UNKNOWN`을 전달한다. `FAIL`은 장착할 수 없고, `UNKNOWN`은 공식 약관 확인 경고를 표시한다.
- `D002`와 `D003`은 `KB_119PLUS_RESTRUCTURING` 중복 그룹으로 강제되며 프론트와 백엔드에서 동시 선택을 차단한다.
- 표시 필드는 `name → name`, `tag → category`, `link → link`로 전달한다.
- 추천 상품의 금융 여부와 유형은 프론트에서 강제하지 않고 백엔드 카탈로그가 판정한다.
- 추천 서비스가 실패하거나 `id/source` 계약을 위반하면 임의의 레거시 상품으로 대체하지 않고 추천 오류를 표시한다.

## 실제 MyData/Open API 연결 시 우선 수집할 값

1. 계좌 잔액: 사업용 계좌의 현재 가용 잔액과 최근 3개월 평균 잔액.
2. 매출 거래: 월별 카드, 현금, 배달 플랫폼 매출과 취소/환불 금액.
3. 지출 거래: 임차료, 인건비, 매입, 공과금, 플랫폼 수수료, 마케팅비, 세금으로 분류한 월별 지출.
4. 대출 정보: 대출별 잔액, 금리, 상환방식, 다음 납부일, 월 납부액, 만기일. 여러 건이면 대출별로 받아 합산한다.
5. 세금 정보: 부가세 및 종합소득세 예상 납부월과 최근 납부액. 현재는 최근 1년 실제 납부액을 연환산 매출로 나눈 개인별 “세금 대비 현금 적립률”을 사용한다.
6. 사업 정보: 업종, 사업 개시일, 주소/상권, 상시근로자 수, 매장 면적. 정책 자격 검증과 업종별 비용 벤치마크에 필요하다.

## MVP에서 직접 입력으로 반드시 받을 값

- 최근 3개월 이상 월매출. 6개월 이상이면 추세와 변동성의 신뢰도가 높아진다.
- 월 총지출과 가능하면 임차료, 인건비, 매입비의 분리값.
- 현재 보유 현금.
- 기존 대출 `있음/내역 없음` 선택. 있음이면 잔액, 월 상환액, 금리, 남은 기간을 모두 받아야 한다.

## 계산 원칙

- 매출은 최근 이력의 추세와 변동성을 사용해 12개월 기준 시나리오를 만든다.
- 몬테카를로는 매출 충격뿐 아니라 변동비와 고정비의 작은 변동도 함께 반영한다.
- 안전자금선은 `고정비 + 해당 월 기존 상환액 + 신규 상환액`으로 매월 다시 계산한다.
- 선택한 KB 상품과 서울시 정책은 추천 API의 식별자를 그대로 넘기고, 공식 URL이 연결된 카탈로그 조건을 우선 사용한다.
- 근거 없는 컨설팅 5% 비용절감, 마케팅 5% 매출상승, 정책지원금 500만원 자동 유입은 사용하지 않는다.
- 정책 공고에 금리·기간·지급시기·자기부담률이 구조화되지 않은 경우 해당 효과는 임의 계산하지 않거나 공식 공고 확인 경고와 함께 제한적으로 계산한다.
- 매출 변동성은 실제 점포 이력으로 계산한다. 업종 이력이 없을 때 고정 15%를 섞지 않는다.

## 아직 남은 고도화 항목

- 실제 MyData API의 대출 상환일이 월 중 현금 부족에 미치는 영향을 일 단위 계산으로 확장한다.
- 세금 납부월, 지원금 실제 지급 지연, 정책별 자기부담·사후정산·중복수혜 조건을 공고별 구조화 데이터로 보강한다.
- 업종/상권별 비용 벤치마크와 계절성을 매출 시나리오에 연결한다.
- 실제 점포 데이터가 쌓인 뒤 XGBoost 기반 매출 분위수(P5/P50/P95) 예측을 보조 모듈로 추가한다.
